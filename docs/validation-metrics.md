# Workflow validation counts

Run `node scripts/validation-report.ts --owner-user-id <id>` with `DATABASE_URL` set in the process environment. It prints one JSON object of the agreed aggregates. Failures print a generic message to stderr and exit nonzero. The report performs reads in one PostgreSQL repeatable-read transaction. It is an operator command: the caller controls database access and must select the intended owner. No labels or educational content are selected or printed.

- `rawNotesByClassAndDay` groups all captured Raw Notes, including subsequently voided notes, by Class ID and the `observed_at` calendar day in the Class's current IANA timezone (`YYYY-MM-DD`). The list is ordered by Class ID, then day. This measures recording activity; it does not infer sessions. Changing a Class timezone can change historical day buckets.
- `proposalDecisions` counts canonical Proposal Items decided by the owner in their Classes, once per item. APPROVED with SQL NULL `teacher_patch` is approved; APPROVED with a non-null patch (including `{}`) is edited; REJECTED is rejected. Product event rows do not establish these decisions. Pending items are excluded.
- `viewEvents` counts stored event rows for each of the five client view names for the owning teacher and Class, including zero counts. `historyOpenCount` equals `history_opened`. These are best-effort UI openings, not unique visits or evidence of a later decision. Retries/reopens can add rows; blocked requests or disabled/unavailable analytics can undercount.
- `closedLoopStudentIssueCount` counts distinct StudentIssue IDs with at least one complete linked path. Approved canonical initial Evidence on that issue must have `observed_at <= intervention.occurred_at`. That Intervention must target the same issue, and the ReassessmentTarget must target that same issue. When the optional Intervention link is supplied it must name that exact Intervention; when absent, any correctly timed Intervention targeting that issue is eligible. The reassessment must be non-cancelled, its target EVIDENCED, and `intervention.occurred_at < outcomeEvidence.observed_at`. Outcome Evidence must belong to the same Student and StudentIssue, link the reassessment, and come from a Raw Note linked to that reassessment. It must be a distinct Evidence with strictly later educational `observed_at` than the initial Evidence. Canonical Evidence retained after source-note voiding remains eligible. Evidence approvals, Intervention and Reassessment creators must be the owner. A same-issue teacher transition must have non-null `from_state`, a different `to_state`, and `created_at >= outcomeEvidence.created_at`. When the transition explicitly references Evidence, it must reference that outcome; manual transitions without an Evidence FK remain eligible. Equal approval/transition timestamps permit one transactional decision batch. Initial creation history and no-op state records never qualify. Transitions need not improve state: reopening is also a teacher-confirmed update. Current issue state, archived state and merged canonical labels do not erase historical paths.
- `reassessmentFollowThroughCount` counts distinct Reassessment IDs with at least one outcome Evidence satisfying the same canonical outcome predicate above, additionally `due_at <= report transaction time` and `outcomeEvidence.observed_at >= due_at`. Multiple evidenced targets count once; skipped-only, cancelled or unrelated Evidence does not qualify. An early outcome can complete a reassessment but does not meet this due-follow-through predicate. This metric does not require an Intervention or a later state transition.

All counts are lifetime counts scoped through `classes.owner_user_id`; no cross-owner aggregate or client assertion supplies canonical closure. Educational chronology uses `observed_at` and `occurred_at`; approval/teacher decision ordering uses `created_at`. A recorded mark-performed click time is not a prerequisite: Task 20 permits approved outcomes while a reassessment is still SCHEDULED and can complete it without `performed_at`. The linked outcome Evidence and EVIDENCED target establish follow-through, including backdated observations. A matching path records workflow use and temporal association, without attributing learning changes or teacher decisions to interventions or history openings.

Request logs use an allowlist serializer and a server-generated UUID, controlled route-operation vocabulary, validated ID shapes, status, elapsed milliseconds and controlled API error codes. Fastify automatic request/error logging and Better Auth diagnostics are disabled. Headers, URLs, bodies and exception objects are never forwarded. The stdout collector operator is responsible for access control and retention. Browser tracking sends only the strict contract's event name, Class ID and optional entity ID, and never delays the workflow on delivery.
